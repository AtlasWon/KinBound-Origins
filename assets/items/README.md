# Item art

Hand-drawn item icons go in this folder. Anything not drawn yet is generated in
code, and the two live side by side permanently -- you can deliver one icon, or
none, and the bag looks finished either way.

```
assets/items/<icon-key>.png            32 x 32, transparent, hard edges
assets/items/<icon-key>-<state>.png    a frame of it -- see "Frames" below
```

## Just dropped some art here?

If it did not come out of a pixel editor -- if it is 1254x1254, or named
`Potion.png`, or anything other than a finished 32x32 icon -- run:

```
npm run item:import
```

It preserves your originals in `source/` (never written to again, never
shipped), recovers the drawing from the encoder's noise by fitting a palette at
full resolution and taking a per-block vote, fits it to the cell, and renames it
to whatever the game actually asks for. It prints every decision and its reason.
`-- --dry` says what it would do without writing anything.

## The name is the icon key

The name is the **icon key** -- the `icon` field in `data/items/items.json` --
and not the item id, not the item name, and not a family name:

| you have | the game wants | why |
|---|---|---|
| `field_vessel.png` | `vessel_field.png` | that is the item **id** |
| `Vessel.png` | `vessel_field.png` | `vessel` is six icons; this is the basic one |
| `Vessel-closed.png` | `vessel_field.png` | "closed" means the icon itself |
| `Vessel-open.png` | `vessel_field-open.png` | "open" is a **frame** |

Keys and item ids are separate so two items can share one drawing.
`npm run item:list` prints every key. `npm run item:check` reads whatever is
here and says what is wrong with it -- including the exact filename a badly
named file should have had.

## Frames

An icon key may own extra drawings of the **same object doing something**. A
vessel is thrown and splits open, and the open one is not an item: nobody holds
it, buys it or counts it, and it never appears in the bag. So it is a frame of
the vessel, named with the state on the end.

The state list is fixed -- `npm run item:check` prints it, with what each one is
for and which icons have delivered one.

**Draw every frame on the same canvas with the object in the same place.** The
frames of one key are seated together, so they stay lined up; drawn separately
and centred separately, the vessel's base would jump the moment the lid opened.

## The three things that catch people

1. **32 x 32.** If you are drawing by hand, work in **2 x 2 blocks** -- the bag
   row shows this file halved, and only block art halves exactly. (Art brought
   in by `npm run item:import` is deliberately not on that grid; the checker
   explains why where it reports it.)
2. **No shadow, no ground, no background.** Unlike a creature, an item is
   *centred* in its cell rather than stood on a line, so anything opaque that is
   not the item pushes the whole drawing off-centre.
3. **Hard edges.** No anti-aliasing. On a canvas this small a soft edge does not
   cost you a fringe, it costs you the shape.

The full spec, written for whoever is drawing, is **`docs/ITEM-SPEC.md`**.

## The rest of the folder

`source/` holds the originals exactly as delivered. Nothing writes to it after
the first import and it is excluded from the installer.

`index.json` is generated by `npm run itemart` and lists what is actually here.
You do not normally need to run it: the dev server and the packaged app both
read the directory live, so a file dropped in is picked up on the next launch.
The written copy is for a plain static host.

To see the whole set, generated and drawn together:

```
node tools/serve.js
npx electron tools/capture.cjs tools/shots/items.js     every icon, 1x and 4x
npx electron tools/capture.cjs tools/shots/itembag.js   a bag, a shop, the frames
```

`node tools/item-placeholders.js` writes three throwaway test files here (and
`--clean` removes them again). They are not art and must never ship.
